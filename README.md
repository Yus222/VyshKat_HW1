 # ВышКат

Консольное приложение для учёта парка прокатного транспорта. Проект выполнен на C# (.NET 8).

## Возможности

- Добавление электросамокатов, велосипедов и электровелосипедов после техосмотра
- Отклонение неисправного транспорта
- Учёт шлемов и зарядных станций
- Общий список имущества с названиями и инвентарными номерами
- Количество транспорта и общее количество объектов на балансе
- Суммарное суточное энергопотребление всех объектов, которые потребляют энергию
- Список транспорта для новичков (простота использования от 6 до 10)

Данные вводятся через консоль. В программе нет заранее созданного парка: все объекты добавляет пользователь.

## Запуск

Требуется **.NET SDK 8**.

Из корневой папки проекта:

```bash
dotnet restore
dotnet build
dotnet run --project VyshKat/VyshKat.csproj
```

Проверка тестов:

```bash
dotnet test
```

Сбор покрытия тестами (Coverlet):

```bash
dotnet test --collect:"XPlat Code Coverage"
```

Отчёт в формате Cobertura появится в папке `VyshKat.Tests/TestResults`.

## Пример работы

После запуска появляется меню:

```text
1. Добавить транспорт
2. Добавить вещь
3. Отчёт по парку
4. Транспорт для новичков
5. Список имущества
0. Выход
```

Сценарии для проверки:

1. Выбрать `1`, создать исправный электросамокат с номером `S-1`, простотой `8` и расходом `2.5`. Техосмотр пройден, самокат принят
2. Выбрать `1`, создать неисправный велосипед. Техосмотр не пройден, велосипед не добавляется
3. Выбрать `2`, добавить шлем с номером `H-1`
4. Выбрать `2`, добавить зарядную станцию с номером `C-1` и расходом `1.2`
5. Выбрать `3`: один транспорт, три объекта, суммарный расход `3.7` кВт·ч
6. Выбрать `4`: отображается самокат `S-1`, так как простота `8 >= 6`
7. Выбрать `5`: видны названия и инвентарные номера всех трёх объектов
8. Попробовать добавить объект с уже занятым номером: программа не добавит его повторно

Дробное энергопотребление можно вводить как через точку, так и через запятую.

## Устройство проекта

- `VyshKat/Models` — транспорт, вещи и их интерфейсы
- `VyshKat/Services/ServiceCenter.cs` — правило техосмотра: исправная техника принимается, неисправная — нет
- `VyshKat/Services/Park.cs` — добавление объектов, проверка номеров, отчёты и выбор техники для новичков
- `VyshKat/ConsoleApp.cs` — меню, чтение данных и вывод результатов
- `VyshKat/Program.cs` — регистрация зависимостей в DI-контейнере
- `VyshKat.Tests` — юнит-тесты и тесты сценариев консольного меню

Транспорт должен проходить техосмотр до добавления в парк. Вещи добавляются отдельно. Один инвентарный номер нельзя назначить двум объектам. Велосипеды и шлемы не потребляют энергию, электросамокаты, электровелосипеды и зарядные станции — потребляют.

## SOLID

**SRP (единственная ответственность).** `Park` отвечает за учёт и запросы к парку, `ServiceCenter` — за решение о техосмотре, `ConsoleApp` — только за взаимодействие с пользователем. Изменение меню не затрагивает правила учёта.

**OCP (открытость для расширения).** Новый вид транспорта можно создать как наследника `Transport` или `ElectricTransport`. Методы подсчёта и хранения в `Park` менять не придётся. При добавлении нового варианта в консольное меню понадобится обновить выбор типов в `ConsoleApp`.

**LSP (подстановка).** `Bicycle`, `ElectricScooter` и `ElectricBike` работают в `Park` через общий тип `Transport`. Методы парка не зависят от конкретного наследника.

**ISP (разделение интерфейсов).** `IInventoryItem` описывает инвентаризацию, а `IEnergyConsumer` — потребление энергии. Шлем и обычный велосипед не обязаны иметь поле энергопотребления.

**DIP (инверсия зависимостей).** `Park` получает `IServiceCenter` через конструктор, а не создаёт `ServiceCenter` самостоятельно. В `Program.cs` реальная реализация связывается с интерфейсом через `Microsoft.Extensions.DependencyInjection`.

Наиболее явно используется **DIP**: в тестах техосмотр заменяется на `FakeServiceCenter` без изменений в `Park`.

Сознательно ограничен **OCP**: `ConsoleApp` содержит простой выбор из известных видов транспорта. При появлении нового вида нужно добавить пункт меню. Для небольшого консольного приложения это проще, чем вводить фабрики и отдельную систему регистрации типов.

## Расширение программы

- **Новый транспорт.** Добавить класс-наследник `Transport` либо `ElectricTransport` и вариант ввода в `ConsoleApp`. `Park`, `ServiceCenter` и отчёты остаются без изменений
- **Сотрудник.** Добавить отдельную модель и сервис учёта сотрудников. Сотрудники не реализуют `IInventoryItem`, поэтому не попадают на баланс парка
- **Склад запчастей.** Добавить модель запчасти, реализующую `IInventoryItem`, и отдельный учёт остатков. Логику техосмотра транспорта менять не требуется

## Тестирование

Используется **xUnit**. В `ParkTests` проверяются допуск и отказ при техосмотре, правило для новичков с границей `6`, суммарная энергия, инвентарные номера, проверка входных данных и запрет добавлять транспорт без техосмотра.

Подмена зависимости реализована в тестах `FakeInspectionCanRejectWorkingTransport`, `FakeInspectionCanAcceptBrokenTransport` и `DependencyInjectionUsesProvidedInspection`. Фейковый `IServiceCenter` возвращает заранее заданный результат. Это позволяет проверить поведение `Park` независимо от реального техосмотра.

`ConsoleAppTests` проверяет ввод и вывод, в том числе успешную приёмку, отказ, отчёты, учёт вещей, дублирующийся номер и ошибочный пользовательский ввод.

## Использование ИИ

Я разработал модель учёта транспорта и имущества, реализовал добавление объектов в парк, проверку инвентарных номеров, расчёт суточного энергопотребления и выбор транспорта для новичков. Основная логика этих операций находится в Services/Park.cs. Модели транспорта и имущества вынесены в папку Models.

ИИ использовался как вспомогательный инструмент. В частности, он помог уточнить разделение интерфейсов IInventoryItem и IEnergyConsumer, разобраться с регистрацией зависимостей в DI-контейнере в Program.cs и подменой IServiceCenter при тестировании. Отдельные рекомендации были использованы при доработке фрагментов кода и проверке граничных случаев в ParkTests.cs. Предложенные варианты я соотносил с существующей структурой проекта и требованиями задания.

Также я выполнил сборку и запуск приложения, проверил через консоль основные сценарии работы: приём и отклонение транспорта после техосмотра, добавление имущества, расчёт энергопотребления и формирование отчётов. После этого запустил автоматическое тестирование: все 23 юнит-теста прошли успешно, покрытие кода составило 91,9%.
